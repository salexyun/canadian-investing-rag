# Roadmap

Step-by-step build plan, tracked against the LLM Zoomcamp rubric (see
[README.md](README.md#evaluation-criteria-checklist)). Update this
file as steps complete — it's the durable, cross-session version of
the todo list; a live version also exists in-session via the task
tool while a session is active.

- [x] Evaluate retrieval approaches — BM25 vs vector vs hybrid (RRF) against the 112-question set (`eval/evaluate_retrieval.py`) *(rubric: Retrieval evaluation)*. Hybrid won overall (hit_rate=0.714/mrr=0.581) but had a nuance: on the plain-language slice it tied vector's hit-rate with slightly *lower* MRR (0.362 vs 0.374) — fusing in a weak bm25 signal dragged down top-1 ranking there. Not the final answer — see reranking below, which fixed this.
- [x] Add cross-encoder reranking (`BAAI/bge-reranker-base`, `rag/reranker.py`) *(rubric best-practices bonus)* — tested on top of both vector and hybrid candidates specifically to target the plain-language MRR gap just found, not added reflexively. Winner at that point: hybrid_rerank, best on every slice tested — overall hit_rate=0.768/mrr=0.659, jargon 0.964/0.858, plain_language 0.571/0.461, numeric_fact 0.741/0.672. Superseded by query rewriting below.
- [x] Extract retrieval into shared `rag/` modules (`vector_search.py`, `hybrid_search.py`, `retriever.py`) — the production RAG flow and the eval script now use the literal same retrieval code, not two implementations that could drift. Verified: re-ran the eval after refactoring, byte-for-byte identical numbers.
- [x] Add query rewriting (`gpt-5.6-luna`, `rag/query_rewrite.py`) *(rubric best-practices bonus)* — tested against the ground-truth set, not assumed. **Biggest single jump in the whole retrieval investigation**: new winner `hybrid_rerank_rewrite`, overall hit_rate=0.875/mrr=0.729. Plain-language slice (the gap chased since the first retrieval eval): hit_rate 0.571→**0.804**, mrr 0.461→**0.651**. numeric_fact: 0.741→0.897 / 0.672→0.805. One honest tradeoff: jargon queries are slightly *worse* with rewriting (hit_rate 0.964→0.946, mrr 0.858→0.807) — rewriting an already-precise query adds a small chance of drift. Net gain heavily outweighs it. **This (query-rewrite → hybrid RRF → rerank) is the final retriever, `rag/retriever.py`.**
- [x] Build the RAG class (`rag/rag.py`) *(rubric: Retrieval flow)* — composition-based (retriever injected), prompt construction is tier-aware (PRIMARY preferred, SECONDARY flagged explicitly) and content_type-aware (effective_date surfaced as "as of" when present). Verified with real questions, not just "it ran": both test answers correct, well-grounded, appropriately hedged, correctly distinguished CIPF/CIRO/CDIC's different roles, real working citation URLs. Model: `gpt-5.6-terra` as a placeholder — LLM evaluation (below) decides terra vs sol for real.

## Next

- [x] Evaluate >=2 LLM approaches for main RAG generation (`eval/evaluate_llm.py`: `gpt-5.6-terra` vs `gpt-5.6-sol`, judge=`gpt-5.5`, deliberately not a candidate — avoids self-preference bias) *(rubric: LLM evaluation)*. Reordered ahead of Langfuse for the same reason the RAG flow was — needed a real-data decision now, not blocked on an external account-creation step. Results (n=30): terra RELEVANT=26/PARTLY=4/avg=0.933, sol RELEVANT=27/PARTLY=3/avg=0.950 — neither had a single NON_RELEVANT answer. Did not mechanically pick sol as "the winner": inspected where the gap came from and it was **one hard edge-case question out of 30**, not a broad quality difference. **Chose terra** — the margin isn't a robust signal at this sample size, and terra costs ~2.5x less on both input and output. Cost decides it when performance is statistically indistinguishable. Fixed a real crash along the way: sharing one Retriever's local PyTorch models (embedder, cross-encoder) across a thread pool segfaulted — restructured so retrieval runs sequentially and both models see identical retrieved context (otherwise query rewriting's own LLM call could give the two models slightly different context, confounding the comparison).
- [x] Set up Langfuse Cloud (free tier) + SDK integration — verified against the actual installed package (`langfuse==4.14.4`) rather than the "install this GitHub skill" guidance Langfuse's own site suggested, which turned out to reference stale/wrong API patterns (`langfuse.decorators`, standalone `langfuse.trace()`) that contradicted the real installed API. `rag/rag.py`/`retriever.py`/`query_rewrite.py` use `langfuse.openai`'s `OpenAI` wrapper (covers `.responses.create`/`.parse`, confirmed via `OPENAI_METHODS_V1`) plus `@observe()` on `RAG.rag()` and `Retriever.search()` to group each user question into one trace. End-to-end verified via the Langfuse API itself, not just "no errors": `auth_check() == True`, and a real trace fetched back showed the correct nested structure — one `rag-answer` trace containing a `retrieve` span with two correctly-attributed generations (`gpt-5.6-luna` for the rewrite, `gpt-5.6-terra` for the answer).
- [x] Build the Streamlit interface, with citations + disclaimer, feedback wired in as one piece (`app/main.py`) *(rubric: Interface + half of Monitoring)*. Not built before feedback wiring and then retrofitted — thumbs up/down needs something to click, so they're naturally the same task, mirroring the coursework's own `app.py` pattern (chat + feedback buttons in one file). `RAG.rag()` now returns a `RAGResult` (answer, trace_id, sources) instead of a bare string, since Streamlit reruns the whole script on every interaction — the trace_id has to be captured at generation time and carried in `st.session_state` until the feedback click, then scored via `create_score(trace_id=...)`, not `score_current_trace()` (no "current" trace context survives the rerun). Verified for real in a browser (`preview_start`), not just code review: asked a real question, confirmed tier-labeled sources rendered (PRIMARY CRA + SECONDARY TD, correctly distinguished), clicked thumbs-up, then queried the Langfuse API directly and confirmed a real `user_feedback=1.0` score landed on the correct trace.
- [x] Build the Langfuse monitoring dashboard *(rubric: rest of Monitoring)* — checked via the API first rather than assumed: `dashboards.list()` showed zero dashboards exist by default for a fresh project, so "5+ charts" had to actually be built, not just confirmed. Built as code (`monitoring/build_dashboard.py`, `lf.api.unstable` dashboards/dashboard_widgets), matching how everything else in this project is built rather than clicked together manually and left undocumented. 6 widgets past the 5-chart minimum: total LLM calls, cost over time, latency (p50) over time, token usage over time, calls by model (terra vs luna in one view), average user feedback score. Every field name (measures, dimensions, filters) verified against the real API before use — several plausible guesses were wrong (`cost`/`model`/`time_to_first_token` all invalid; `totalCost`/`providedModelName` are correct). Verified by fetching the dashboard back afterward and confirming all 6 placements landed with correct grid positions, not just that the create calls returned success.
- [x] Flesh out `docker-compose.yml` to run end-to-end — app + Qdrant only; no self-hosted Postgres/Grafana, Langfuse Cloud is external *(rubric: Containerization)*. Reviewing before assuming it worked turned up three real bugs, all fixed: (1) `rag/vector_search.py` hardcoded `QDRANT_URL` to `localhost:6333` instead of reading the env var like `ingestion/load_vector_store.py` did — would silently fail to retrieve anything in a container, where `localhost` means the container itself. Fixed by reading `os.getenv`, then handled the local-vs-Docker hostname duality by keeping `.env`'s `QDRANT_URL=http://localhost:6333` for local dev and overriding it to `vector-db:6333` in `docker-compose.yml`'s `environment:` (which wins over `env_file:`), rather than forking `.env` into two copies. (2) No `.dockerignore` — `COPY . .` would have baked the 1.3GB host `.venv` (wrong platform/arch) and `.env` (secrets) straight into the image. (3) Built image was 8.95GB because `torch`'s default Linux wheel drags in the full CUDA/nvidia stack for a project that only does small-model CPU inference (bge-small, bge-reranker-base) — no GPU anywhere this runs. Fixed via `[tool.uv.sources]` with a `platform_system == 'Linux'` marker pointing at PyTorch's CPU-only wheel index (had to also promote `torch` to a direct dependency — the marker override silently didn't apply while it was only a transitive dep of `sentence-transformers`); image dropped to 2.22GB, build time 158s→85s. Verified for real, not just "it built": `docker compose up -d --build` (the exact single command a grader runs), asked a real question through the browser against the containerized app, got a correct answer with 4 correctly tier-ordered sources (3 PRIMARY CRA, 1 SECONDARY RBC), clicked thumbs-up, then confirmed via the Langfuse API that a real `user_feedback=1.0` score landed on a well-formed trace (`rag-answer` → `retrieve` span + 2 `GENERATION`s) — all from inside the container, over the real network, not mocked. Also confirmed the named `qdrant_storage` volume persists data across `down`/`up` cycles, and that local (non-Docker) `uv run` dev still resolves `QDRANT_URL` to `localhost` correctly after the fix.
- [x] Orchestrate the ingestion pipeline with Kestra *(rubric: Ingestion pipeline, 2-point tier)* — the rubric lists Kestra/dlt/Airflow/Prefect as equivalent options, but they're not actually interchangeable: dlt is an extract-and-load *library* (no scheduler, no server, typically called *from* one of the other three), not an orchestrator, so "dlt vs Kestra" wasn't really the choice once that was untangled. Picked Kestra over Airflow/Prefect on task fit + relevance: Airflow's scheduler+webserver+metadata-DB stack is real overkill for a linear 3-step non-scheduled pipeline (the same "too heavy for course-project scale" reasoning already applied against self-hosted Langfuse/Grafana), and Kestra is literally [what LLM Zoomcamp Module 3 teaches](https://github.com/DataTalksClub/llm-zoomcamp/tree/main/03-orchestration) for this exact category, plus currently the fastest-growing/most-discussed of the three ($25M Series A, Bloomberg/Toyota/JPMorgan adoption). Runs standalone (`server local`, embedded H2, no Postgres — same "right-sized, not production-HA" call as everywhere else) as one new `kestra` service in `docker-compose.yml`. Fetch/chunk/load scripts themselves are untouched — orchestrated via a new `ingestion` image (`ingestion/Dockerfile`, adds the Playwright/Chromium binary the serving `app` image deliberately doesn't have) that Kestra's Docker task runner launches as sibling containers on the compose network (`flows/ingestion.yml`). Verified for real, not just "the YAML looks right" — caught and fixed two genuine bugs by actually executing it: `env` isn't a valid field under `taskRunner` (belongs on the task itself — a real schema-validation rejection, not a guess), and Kestra's Docker task runner sets an empty per-execution temp dir as the container's working directory, not the image's `/app` (needed an explicit `cd /app &&`). A scoped test run (`only_ids=rbc_tfsa`, added as a flow input specifically so verification doesn't require sitting through the full ~93-page/hour-plus fetch) went green end-to-end: fetched over the real network, `chunk`'s `--only` correctly merged into the existing 1,052-chunk corpus without clobbering it, and `load` reached `vector-db` by its compose-network hostname and brought Qdrant back to exactly 1,052 points. Confirmed the fetch really hit the live page (not a no-op) via a `content_hash` match against the file on disk, not just a "SUCCESS" status.

## Decisions made along the way (and why)

- **Monitoring/eval: Langfuse Cloud, not Grafana+Postgres (the course's approach) or self-hosted Langfuse.**
  Self-hosted Langfuse is a 6-service stack (Postgres + ClickHouse + Redis +
  MinIO + web + worker, ~4 cores/16GB recommended) — too heavy for this
  project's traffic scale alongside Qdrant + our own app. Cloud free tier
  gets the same SDK/tracing/eval/dashboard features without managing any
  database ourselves — same reasoning as calling the OpenAI API instead of
  self-hosting an LLM.
- **Not Arize Phoenix** — also a strong fit (retrieval-eval templates,
  embedding visualization), but chosen against in favour of learning
  Langfuse specifically; a deliberate choice, not an oversight.
- **`rag/`'s RAG class is composition-based** (a retriever passed into one
  class), not the course's 3-level `RAGBase`/`RAGVector`/`RAGPgVector`
  subclass hierarchy — we don't swap retrieval backends at runtime in
  production, just compare 3 approaches once and pick a winner; less
  structure is genuinely enough here.
- **Different LLM per task, not one model everywhere.** Checked current
  OpenAI pricing directly against the API (`client.models.list()`), not
  an aggregator estimate — `gpt-5.6` (luna/terra/sol) is the current
  generation, one past the coursework's `gpt-5.4-mini`. Bulk/simple
  tasks (ground-truth generation, query rewriting) use
  `gpt-5.6-luna` (cheapest current tier, $0.20/$1.20 per 1M tokens) —
  no reasoning depth needed for either. Main RAG generation and the
  LLM-judge deliberately *don't* have a model picked yet — task
  "Evaluate >=2 LLM approaches" is where that gets decided empirically
  (comparing `gpt-5.6-terra` vs `gpt-5.6-sol`), not guessed ahead of it.
- **BM25 vs vector: real divergence found, not just the theoretical
  case.** Same 3 test queries run against both: on a jargon-exact query
  both landed the correct chunk top-1; on a fully-paraphrased query
  ("what happens to my investments if I leave Canada" — zero shared
  vocabulary with "non-resident"), BM25's top 3 were all irrelevant
  while vector search's top 3 were all correct. Confirms hybrid is
  worth the eval effort, not just plausible in theory.
