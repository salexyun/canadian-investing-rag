# Roadmap

Step-by-step build plan for the Canadian Investing Assistant. Update
this file as steps complete — it's the durable, cross-session version
of the todo list; a live version also exists in-session via the task
tool while a session is active.

- [x] Build retrieval evaluation question set — 112 questions from 56 stratified-sampled chunks, jargon-exact + newcomer-plain-language pairs, `gpt-5.6-luna`, $0.03 (`eval/build_ground_truth.py`)

- [x] Evaluate retrieval approaches — BM25 vs vector vs hybrid (RRF) against the 112-question set (`eval/evaluate_retrieval.py`). Hybrid won overall (hit_rate=0.714/mrr=0.581) but had a nuance: on the plain-language slice it tied vector's hit-rate with slightly *lower* MRR (0.362 vs 0.374) — fusing in a weak bm25 signal dragged down top-1 ranking there. Not the final answer — see reranking below, which fixed this.
- [x] Add cross-encoder reranking (`BAAI/bge-reranker-base`, `rag/reranker.py`) — tested on top of both vector and hybrid candidates specifically to target the plain-language MRR gap just found, not added reflexively. Winner at that point: hybrid_rerank, best on every slice tested — overall hit_rate=0.768/mrr=0.659, jargon 0.964/0.858, plain_language 0.571/0.461, numeric_fact 0.741/0.672. Superseded by query rewriting below.
- [x] Extract retrieval into shared `rag/` modules (`vector_search.py`, `hybrid_search.py`, `retriever.py`) — the production RAG flow and the eval script now use the literal same retrieval code, not two implementations that could drift. Verified: re-ran the eval after refactoring, byte-for-byte identical numbers.
- [x] Add query rewriting (`gpt-5.6-luna`, `rag/query_rewrite.py`) — tested against the ground-truth set, not assumed. **Biggest single jump in the whole retrieval investigation**: new winner `hybrid_rerank_rewrite`, overall hit_rate=0.875/mrr=0.729. Plain-language slice (the gap chased since the first retrieval eval): hit_rate 0.571→**0.804**, mrr 0.461→**0.651**. numeric_fact: 0.741→0.897 / 0.672→0.805. One honest tradeoff: jargon queries are slightly *worse* with rewriting (hit_rate 0.964→0.946, mrr 0.858→0.807) — rewriting an already-precise query adds a small chance of drift. Net gain heavily outweighs it. **This (query-rewrite → hybrid RRF → rerank) is the final retriever, `rag/retriever.py`.**
- [x] Build the RAG class (`rag/rag.py`) — composition-based (retriever injected), prompt construction is tier-aware (PRIMARY preferred, SECONDARY flagged explicitly) and content_type-aware (effective_date surfaced as "as of" when present). Verified with real questions, not just "it ran": both test answers correct, well-grounded, appropriately hedged, correctly distinguished CIPF/CIRO/CDIC's different roles, real working citation URLs. Model: `gpt-5.6-terra` as a placeholder — LLM evaluation (below) decides terra vs sol for real.

## Next

- [x] Evaluate >=2 LLM approaches for main RAG generation (`eval/evaluate_llm.py`: `gpt-5.6-terra` vs `gpt-5.6-sol`, judge=`gpt-5.5`, deliberately not a candidate — avoids self-preference bias). Reordered ahead of Langfuse for the same reason the RAG flow was — needed a real-data decision now, not blocked on an external account-creation step. Results (n=30): terra RELEVANT=26/PARTLY=4/avg=0.933, sol RELEVANT=27/PARTLY=3/avg=0.950 — neither had a single NON_RELEVANT answer. Did not mechanically pick sol as "the winner": inspected where the gap came from and it was **one hard edge-case question out of 30**, not a broad quality difference. **Chose terra** — the margin isn't a robust signal at this sample size, and terra costs ~2.5x less on both input and output. Cost decides it when performance is statistically indistinguishable. Fixed a real crash along the way: sharing one Retriever's local PyTorch models (embedder, cross-encoder) across a thread pool segfaulted — restructured so retrieval runs sequentially and both models see identical retrieved context (otherwise query rewriting's own LLM call could give the two models slightly different context, confounding the comparison).
- [x] Set up Langfuse Cloud (free tier) + SDK integration — verified against the actual installed package (`langfuse==4.14.4`) rather than the "install this GitHub skill" guidance Langfuse's own site suggested, which turned out to reference stale/wrong API patterns (`langfuse.decorators`, standalone `langfuse.trace()`) that contradicted the real installed API. `rag/rag.py`/`retriever.py`/`query_rewrite.py` use `langfuse.openai`'s `OpenAI` wrapper (covers `.responses.create`/`.parse`, confirmed via `OPENAI_METHODS_V1`) plus `@observe()` on `RAG.rag()` and `Retriever.search()` to group each user question into one trace. End-to-end verified via the Langfuse API itself, not just "no errors": `auth_check() == True`, and a real trace fetched back showed the correct nested structure — one `rag-answer` trace containing a `retrieve` span with two correctly-attributed generations (`gpt-5.6-luna` for the rewrite, `gpt-5.6-terra` for the answer).

- [x] Flesh out `docker-compose.yml` to run end-to-end — app + Qdrant only; no self-hosted Postgres/Grafana, Langfuse Cloud is external. Reviewing before assuming it worked turned up three real bugs, all fixed: (1) `rag/vector_search.py` hardcoded `QDRANT_URL` to `localhost:6333` instead of reading the env var like `ingestion/load_vector_store.py` did — would silently fail to retrieve anything in a container, where `localhost` means the container itself. Fixed by reading `os.getenv`, then handled the local-vs-Docker hostname duality by keeping `.env`'s `QDRANT_URL=http://localhost:6333` for local dev and overriding it to `vector-db:6333` in `docker-compose.yml`'s `environment:` (which wins over `env_file:`), rather than forking `.env` into two copies. (2) No `.dockerignore` — `COPY . .` would have baked the 1.3GB host `.venv` (wrong platform/arch) and `.env` (secrets) straight into the image. (3) Built image was 8.95GB because `torch`'s default Linux wheel drags in the full CUDA/nvidia stack for a project that only does small-model CPU inference (bge-small, bge-reranker-base) — no GPU anywhere this runs. Fixed via `[tool.uv.sources]` with a `platform_system == 'Linux'` marker pointing at PyTorch's CPU-only wheel index (had to also promote `torch` to a direct dependency — the marker override silently didn't apply while it was only a transitive dep of `sentence-transformers`); image dropped to 2.22GB, build time 158s→85s. Verified for real, not just "it built": `docker compose up -d --build` (the exact single command a new user runs), asked a real question through the browser against the containerized app, got a correct answer with 4 correctly tier-ordered sources (3 PRIMARY CRA, 1 SECONDARY RBC), clicked thumbs-up, then confirmed via the Langfuse API that a real `user_feedback=1.0` score landed on a well-formed trace (`rag-answer` → `retrieve` span + 2 `GENERATION`s) — all from inside the container, over the real network, not mocked. Also confirmed the named `qdrant_storage` volume persists data across `down`/`up` cycles, and that local (non-Docker) `uv run` dev still resolves `QDRANT_URL` to `localhost` correctly after the fix.
- [x] Orchestrate the ingestion pipeline with Kestra — considered Kestra/dlt/Airflow/Prefect, but the first two aren't actually interchangeable: dlt is an extract-and-load *library* (no scheduler, no server, typically called *from* one of the other three), not an orchestrator. ## Decisions made along the way (and why)

- **Monitoring/eval: Langfuse Cloud, not a self-hosted Grafana+Postgres stack or self-hosted Langfuse.**
  Self-hosted Langfuse is a 6-service stack (Postgres + ClickHouse + Redis +
  MinIO + web + worker, ~4 cores/16GB recommended) — too heavy for this
  project's traffic scale alongside Qdrant + our own app. Cloud free tier
  gets the same SDK/tracing/eval/dashboard features without managing any
  database ourselves — same reasoning as calling the OpenAI API instead of
  self-hosting an LLM.
- **Not Arize Phoenix** — also a strong fit (retrieval-eval templates,
  embedding visualization), but chosen against in favour of learning
  Langfuse specifically; a deliberate choice, not an oversight.
- **`rag/`'s RAG class is composition-based** (a retriever passed into one
  class), not a 3-level `RAGBase`/`RAGVector`/`RAGPgVector`
  subclass hierarchy — we don't swap retrieval backends at runtime in
  production, just compare 3 approaches once and pick a winner; less
  structure is genuinely enough here.
- **Different LLM per task, not one model everywhere.** Checked current
  OpenAI pricing directly against the API (`client.models.list()`), not
  an aggregator estimate — `gpt-5.6` (luna/terra/sol) is the current
  generation, one past `gpt-5.4-mini`. Bulk/simple
  tasks (ground-truth generation, query rewriting) use
  `gpt-5.6-luna` (cheapest current tier, $0.20/$1.20 per 1M tokens) —
  no reasoning depth needed for either. Main RAG generation and the
  LLM-judge deliberately *don't* have a model picked yet — task
  "Evaluate >=2 LLM approaches" is where that gets decided empirically
  (comparing `gpt-5.6-terra` vs `gpt-5.6-sol`), not guessed ahead of it.
- **BM25 vs vector: real divergence found, not just the theoretical
  case.** Same 3 test queries run against both: on a jargon-exact query
  both landed the correct chunk top-1; on a fully-paraphrased query
  ("what happens to my investments if I leave Canada" — zero shared
  vocabulary with "non-resident"), BM25's top 3 were all irrelevant
  while vector search's top 3 were all correct. Confirms hybrid is
  worth the eval effort, not just plausible in theory.
